### 3.18 The declaration-support check — asking the engine instead of the source

**Not a build-order step.** `check:style-contract` rule 1 has been live since S3 and answers *is this
style-prop value statically extractable?* — the question `plan.md` §3.5's contract is written in. It
is not the question a reader has. `<Box mt="4x" />` and `<Box bg="bg.pannel" />` both satisfy it,
both extract cleanly, and both emit a declaration no browser parses. The class is generated, the
element wears it, the property is never set, and every check in the repo is green.

**The gap was one door wide and it had something behind it.** The first run found ten rejected
declarations: two in our own docs source, seven from `@chakra-ui/panda-preset`'s recipe bodies, and
one obsolete vendor property. None of them was visible to anything the repo already ran.

**D-178 is where the oracle runs, D-179 is what to do with a defect that is not ours, and D-180 is a
procedure that had been quietly returning the wrong number since S5.**

---

**D-178 · The oracle is `CSS.supports` in real Chromium, driven from a Node script through
Playwright**
— **Decision.** `check:declaration-support` reads both generated stylesheets, scans every
declaration out of them, and puts each distinct `property: value` pair to
`CSS.supports(property, value)` in a browser launched by `playwright` — already a root
devDependency, already installed in CI for the `test` matrix's browser leg. The extraction, the
deduplication and the allowance register are pure and unit-tested in the `unit` project; only the
oracle needs the browser. It joins the `styling` job, which gains a
`playwright install --with-deps --only-shell` step.
— **Rejected.** *A `browser`-project test*, the `check:floating-zindex` shape — that check's subject
is a live component under interleaved reactive writes and only exists inside a running app; this
one's subject is **two files on disk**, one of them built by a different Panda run in another
package, and the browser project resolves modules rather than sibling build artifacts. It also
belongs beside the other read-what-Panda-emitted checks, and as a browser test a failure would read
as a component regression. *A Node CSS parser* — css-tree's lexer answers *does the spec's syntax
definition admit this?*, which is a second implementation of the value grammar and a different
question; `prior-art.md` §8.1 forbids exactly that substitution. *A token-union check*, prototyped in
an earlier session and never committed — compare each value against the union of registered token
keys. It produced **only** false positives, because the union is not the set of legal values: a
utility takes raw CSS alongside tokens, so `w="50%"` and `color="#fff"` fail it while `mt="4x"`
passes for the wrong reason. Recorded here so it is not built a second time.
— **Effect.** The `styling` job is now the only one outside the `test` matrix that installs a
browser, and that cost is the decision. What it buys is that the check answers with the engine's own
verdict rather than a model of it: asked to parse each rejected pair into a `CSSStyleSheet`, the same
engine returned an empty value for every one and `red` for `color: red`, so *rejected* and *dropped
by the parser* are one fact here rather than a proxy. The check also generalises what
`testing.md` §3.7's last row previously answered case by case, and it comes up green on `cursor`
because the `cursor.switch` delta of **D-71** is in place.
— **Settled.** S6, 2026-08-10, against a break test in both directions: `mt="4x"` and
`bg="bg.pannel"` added to the docs source are both reported with file, line and selector; a
stale allowance, a malformed register row, an emptied sheet and a missing sheet each fail with their
own message; and the canary fails the run if `CSS.supports` ever stops discriminating.
— **Reasoning.** `testing.md` §8.4; `definition-of-done.md` rule 1.14.

**D-179 · A declaration we did not author is a register row, not a value fix — and the register is
scoped per selector**
— **Decision.** `declaration-support.config.ts` at the repo root holds one row per emitted
declaration that is **not ours to repair**: Panda's own preflight, or a recipe body inside
`@chakra-ui/panda-preset`, which `CLAUDE.md` says we depend on and never vendor. Each row carries the
property, the value, **the list of selectors it is forgiven under**, why, and what deletes it. An
entry that matches nothing fails the check. Nothing is filed and nobody is contacted (**D-110**).
— **Rejected.** *A prose table in `definition-of-done.md`*, the shape §5 and §6 take — those are
prose because their checks do not exist and a person is the only reader; this one has a machine
reader today, and a hand-parsed markdown table would put a second grammar between the rule and its
enforcement. *One row per property/value pair, unscoped* — `transitionDuration: "normal"` reaches
four recipes and a preset bump repairs them one at a time, so an unscoped row would go on forgiving
the three that were never fixed. *Excluding the preset's `staticCss` output from the check
altogether* — it would have hidden all seven upstream findings, including a Tabs rule that silently
loses its `margin-inline-end`.
— **Effect.** Eight rows, twelve selectors, all twelve matching today. Five distinct upstream
defects are now written down where the next preset bump will re-derive them: `transition-duration:
normal` and `transition-timing-function: default` (token references to keys the preset does not
register — **D-71**'s shape at two more scales), `font-feature-settings: pnum` (an OpenType tag that
needed quoting), `background: currentBg` (a Chakra runtime-theme value with no Panda token behind
it), and `not-last: var(--line-offset)` — **not a CSS property at all**: the Tabs recipe writes
`marginEnd: { _notLast: … }`, `_notLast` is not a condition this config's Panda knows, an unknown
condition key is emitted as a kebab-cased property, and the margin it was guarding is lost. The sheet
carries no `:not(:last-child)` rule anywhere, which is how it was found.
— **Settled.** S6, 2026-08-10. The one finding that **was** ours got a value fix rather than a row:
`MdxPagination` passed `direction="Previous"` to a capitalized component, Panda's
`jsxStyleProps: "all"` extracts style props from any capitalized JSX component, `direction` is a real
CSS property and `"Previous"` is not one of its two values. Renamed to `label` in the same commit.
— **Reasoning.** `testing.md` §8.4; `declaration-support.config.ts`'s own header.

**D-180 · The enforcement census excludes ruled-out names as a class, through a register the
procedure reads**
— **Decision.** `definition-of-done.md` §7b carries a ```` ```ruled-out ```` block naming every
`check:*` the corpus introduces **in order to reject it**, with where each is named. The runnable
procedure reads that block instead of carrying a literal `grep -v`. Names are listed bare, without
the `check:` prefix, so the register does not have to exclude itself from the grep it feeds.
— **Rejected.** *A second `grep -v` beside the first* — the shape that failed; a third ruled-out name
would fail it again the same way. *A marker at each mention*, an HTML comment on the line the name
appears on — it survives nothing, because re-wrapping a paragraph moves the name off the marked
line. *Counting the ruled-out names* — they are not enforcement, and a census that counts them
reports a number no reader can act on.
— **Effect.** The census reads **48 named / 23 written / 25 unwritten / 0 unnamed**, and reproduces.
The honest figures were **47/22/25/0** at S4 and stayed there; the *documented* procedure has
returned 48/26 since `check:citations` was introduced at `decisions-ledger.md` §3.16, verified at three
consecutive `HEAD`s, so this is not build drift. It is the defect §7b named in the same paragraph
that caused it: *"the next person to run the procedure gets 48 and cannot tell whether something was
added or whether they ran it wrong."*
— **Settled.** S6, 2026-08-10. Closes the exclusion §7b left as one literal at S4.
— **Reasoning.** `definition-of-done.md` §7b.
