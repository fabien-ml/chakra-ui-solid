### 3.19 The docs site's own chrome — the first consumer stops writing `css()` beside a `<div>`

**Not a build-order step.** `docs-site.md` §1.1 claims the docs app is *a consumer, and that is
load-bearing rather than incidental*. Twelve files of its own chrome wrote `css({ … })` on a raw
`<div>`, which is what a consumer writes when the component layer does not work for them — 58 calls,
none of them touching `Box`. The site was evidence that a consumer's **build** works and evidence of
nothing about the thing the build is for.

**Three decisions, and only the first is the sweep.** D-182 answers a question the sweep was expected
to leave open — whether a descendant selector is a reason to keep a `css()` class — and it turns out
not to be one. D-183 is the cost the conversion measured: `as` cannot carry an element's own
attributes, so nine sites needed the `render` prop.

---

**D-181 · The site's chrome is `Box` and style props; the `css()` that survives is on an element the
site does not render**
— **Decision.** Every one of the twelve files converts. `<div class={css({ display: "flex" })}>`
becomes `<Box display="flex">`, and the element type is preserved through `as` — a `<nav>`, a
`<table>` or an `<aside>` that became a `<div>` would be an accessibility regression wearing a
styling change. Three files keep `css()`, and the criterion is stated rather than enumerated: **the
element is not ours to render.** `layout.ts` styles `<body>`, which the root layout emits itself and
which has no component above it; `prose.ts` styles the elements an `.mdx` page produces; and
`code-pane.ts` styles the `<pre>` Shiki hands back through the MDX `pre` mapping.
— **Rejected.** *Leaving the chrome and letting the component pages carry the claim* — a component
page is MDX prose plus an example, and the chrome is the largest body of hand-written TSX in the app;
it is what anyone opening the site's source actually reads. *A `chakra.div`-style factory* — Chakra's
factory exists because Emotion needs a registration point. Ours has none by construction:
`jsxStyleProps: "all"` reads style props off **any** capitalized component (`plan.md` §3.4), so `Box`
is already the whole mechanism and a factory would be a second one. *Redesigning while converting* —
a substitution and a redesign in one diff hide each other, and the substitution is the evidence.
— **Effect.** 58 `css()` calls across twelve files, down to zero; three remain, one per exception
file, each with the reason in a comment beside it. **The rendered `class` attribute is unchanged,
name for name and in order** — `css({ fontSize: "md", … })` and `<Box fontSize="md" …>` reach the
same `css()` call inside `renderStyled`, so a step heading still carries
`fs_md fw_semibold c_fg mt_0.5 mb_2`. **An inline `style` already in one of the twelve is judged by
whether its value is static, not by the fact that it was already an attribute** — a `css()` call is
the subject of the sweep, but a hand-written `style` that a style prop could carry is the same
failure to use the component layer. Of the two, the pager's text alignment converts:
`textAlign={isNext() ? "end" : "start"}` is a ternary between two literals, so Panda generates both
`.ta_start` and `.ta_end` — the shape `site/link-button` already uses for its two looks. The table of
contents' per-heading indent does not and cannot: the depth is a number no source file writes, and
`check:style-contract` rule 1 rejects a template with an expression precisely because the class it
would name was never generated.
— **Settled.** S6, 2026-08-10, against the running site rather than the suite
(`definition-of-done.md` rule 7.6): the home page, a Get Started page, a Framework page, the Box
component page and a 404, in both colour modes, at 1280px and at 375px where the sidebar and the
table of contents drop out. No console message of any level on any of them.
— **Reasoning.** `docs-site.md` §1.1; `definition-of-done.md` rule 7.10.

**D-182 · A descendant selector is Box's `css` prop, not a reason to keep a class**
— **Decision.** A rule the chrome needs and a style prop cannot express — a selector reaching into
markup we do not render — goes on **Box's `css` escape hatch**, which Panda extracts from the JSX
attribute exactly as it extracts a style prop, and which `renderStyled` merges as a sibling `css()`
argument at the same precedence step as the style props (`component-blueprint.md` §3.4). Two of the
twelve needed it: the source pane beside a live example (`& pre`, `& span` — Shiki's markup inside an
`innerHTML`) and a card's body (`& p` — MDX's paragraph).
— **Rejected.** *Two more rows on the exception list* — the predicted outcome, and wrong. In both
cases the element wearing the class **is** ours: a `<div>` this file renders. What makes an exception
is the element, not the selector, and enumerating a fourth case would have turned a criterion back
into a list. *A Box plus a module-level descendant class beside it* — two mechanisms for one rule,
and the class half is still `css()` on an element we render.
— **Effect.** The exception list stays at three and now has a test rather than a membership. The
route was not invented here: `code-tabs.tsx` has used the `css` prop for Shiki's `<pre>` since the
landing page landed at S5, and nothing pointed at it as the general answer.
— **Settled.** S6, 2026-08-10. The two converted panes were checked by computed style, not by class
name (`plan.md` §0.2): the example's source `<pre>` reports `border-top-width: 0px`,
`border-bottom-left-radius: 4px` and Shiki's light-mode token colour, which is what the module-level
class produced.
— **Reasoning.** `component-blueprint.md` §3.4; `plan.md` §3.5.

**D-183 · An element's own attributes reach it through `render`, never through `as`**
— **Decision.** `BoxProps` is `JSX.HTMLAttributes<HTMLElement>` with the seven displaced style props
patched out, and `as` is a loose `ValidComponent` that **never re-types it**
(`component-blueprint.md` §4). So `<Box as="button" type="button">`, `<Box as="a" href="…">` and
`<Box as="svg" viewBox="…">` are all type errors — by design rather than by omission — and the route
for each is the `render` prop: a function receiving Box's computed props and returning the element
(`component-blueprint.md` §3.5).
— **Rejected.** *Widening `BoxProps` so `as` narrows it* — the deep conditional polymorphic types
that needs are the cost §4 refuses by name, and the IntelliSense bill lands on every consumer, not on
us. *A cast per call site* — it type-checks, and a silently swallowed `href` is the failure the types
exist to make loud. *Keeping the raw element* — the thing this entry is undoing.
— **Effect.** Nine `render` props across seven of the twelve files: three in the colour-mode toggle
alone — the `<button type>` and both `<svg viewBox>` icons — and one each where a router `Link`, a
`DocLink` or an external `<a href>` is the target. The one file that reaches `as="a"` instead is
`mdx-components.tsx`, and it does so for a reason that does not generalise: MDX hands the mapping a
`Record<string, unknown>` bag with `href` already inside it, so the cast lands on the **spread**
rather than on a named attribute. This is a real ergonomic cost against Chakra, where
`<chakra.a href>` type-checks, and it is the price of §4's flat layering rather than an oversight.
— **Settled.** S6, 2026-08-10, probed rather than assumed: all three shapes above were written into
`apps/docs/src` and `pnpm --filter @chakra-ui-solid/docs typecheck` rejected each with `TS2322`
naming the missing property.
— **Reasoning.** `component-blueprint.md` §3.5, §4; `packages/system/src/render-styled/render-styled.tsx`.
