### 8.4 `check:declaration-support` — the emitted declaration, put to the engine

**What it is for.** §6.1's rule 1 (`style-prop-static-value`) asks whether a style-prop value is
statically **extractable**. That is the right question for `plan.md` §3.5's contract, and it is not
the question a reader has. Both of these satisfy rule 1:

```tsx
<Box mt="4x" />          // static, extractable, and not a spacing token
<Box bg="bg.pannel" />   // static, extractable, and a typo
```

Panda emits the raw value when a token does not resolve, so the sheet gets `margin-top: 4x` and
`background: bg.pannel`. The class is generated, the element wears it, and **the property is never
set** — no warning, no console message, no failing test. `plan.md` §0.2's hazard, arriving through
the one door the style contract leaves open.

**The oracle is `CSS.supports(property, value)`**, asked of a real engine over the generated
stylesheet: *does the browser understand the declaration Panda actually wrote?* rather than *did the
source literal look plausible?*

**It is a general form of what §3.7's last row describes.** That row names one instance — the
preset's `cursor: "switch"` against a token registered as `swittch` — and answers it with a
computed-style assertion plus `check:preset-token-resolution` for the specific case. This check is
the same failure asked of every declaration in the sheet at once, and it passes on `cursor` today
precisely because our one-key delta is in place.

**What it is not.** Four checks sit near it and none of them is this one:

| Check | Its question |
|---|---|
| `check:style-contract` rule 1 | Can Panda **extract** this value from our source? |
| `check:css-coverage` (§3) | Is the class our component computes **present** in the sheet? |
| `check:preset-token-resolution` (§8) | Does *one named* broken token reference still degrade quietly, and does our delta fix it? |
| **this one** | Does the declaration in the emitted rule **parse**? |

A value can pass all three of the others and still render nothing, which is why it exists.

---

**Input.** Both generated stylesheets, read from disk after `cssgen`:

- `packages/styled-system/styled-system/styles.css` — our own config over
  `packages/{system,components}/src`, plus the preset's `staticCss` recipes and Panda's preflight.
- `apps/docs/styled-system/styles.css` — **a consumer's build**: `apps/docs/panda.config.ts` over the
  docs app's source (`docs-site.md` §1.1). It is the only sheet that carries the style props anyone
  writes today, and it is where the first run's own finding was.

Two Panda runs on purpose, and reading only the first would have missed the finding entirely.

**Where the oracle runs, and what was rejected** (`decisions.md` **D-178**). `CSS.supports` needs a
browser and every other `check:*` is a Node script, so the choice was real:

- **Chosen: a Node script that drives Chromium through Playwright.** `playwright` is already a root
  devDependency and CI already installs the browser for the `test` matrix's browser leg. The check
  keeps the house shape — `scripts/check-declaration-support.mjs`, logic in `scripts/lib/`, unit
  tests beside it — and the answer comes from the engine itself.
- **Rejected: a `browser`-project test**, the `check:floating-zindex` shape. That check's subject is a
  *live component* under interleaved reactive writes, which only exists inside a running app. This
  one's subject is a **file** — two of them, one built by a different Panda run in another package —
  and the browser project resolves modules, not sibling build artifacts. It also belongs in the
  `styling` job with the other read-what-Panda-emitted checks; as a browser test a failure would read
  as a component regression.
- **Rejected: a Node CSS parser** (css-tree's lexer, or equivalent). It answers *does the spec's
  syntax definition admit this?*, which is a second implementation of the value grammar and not the
  same question. `prior-art.md` §8.1: measure the dependency, do not reason about its source.
- **Rejected, and previously prototyped: a token-union check** — compare each value against the union
  of registered token keys. It produced **only** false positives, because the union is not the set of
  legal values: a utility accepts raw CSS alongside tokens, so `w="50%"` and `color="#fff"` fail it
  while `mt="4x"` passes for the wrong reason.

**Cost, stated:** the `styling` job gains a `playwright install --with-deps --only-shell` step.

**Algorithm.**

1. **Scan** each sheet into declarations — property, value, the innermost enclosing block, and the
   line. A scanner rather than a regex, because a CSS value contains every character that would
   otherwise end one: `url(data:…;base64,…)` carries a `;`, `content: "}"` carries a brace,
   `grid-template-areas` spans lines, and **Panda escapes class names** — `.w_1\/2`, `.p_4\.5`.
2. **Drop what the oracle cannot judge**, counting each: custom properties, and declarations inside
   at-rules whose contents are descriptors rather than properties (`@font-face`, `@property`).
3. **Strip `!important`** — `CSS.supports("display", "none !important")` is false, so leaving it on
   would report every one of them.
4. **Deduplicate** into distinct `property: value` pairs — the two sheets carry 12,574 declarations,
   of which 9,056 are judgeable and those are **1,133 distinct pairs**, asked in one round trip.
5. **Ask the canary first**, then the pairs. Rejections are matched against the allowance register;
   anything left fails.

**The canary.** Before any pair is judged, the page is asked for `CSS.supports("color", "red")` and
`CSS.supports("margin-top", "4x")` and must get `true` and `false`. If the oracle ever stops
discriminating, every pair comes back accepted and the check reports green over a broken sheet —
§3.5's configuration canary, one check over.

**The allow-list.** `declaration-support.config.ts` at the repo root, one row per emitted
declaration that is **not ours to repair**: Panda's own preflight, or a recipe body inside
`@chakra-ui/panda-preset`, which `CLAUDE.md` says we depend on and never vendor. It is a config file
rather than a table here for §8.3's reason — it has a machine reader, and `attribution.config.ts` is
the precedent. Three properties make it a register rather than a list of excuses:

- **Scoping is per selector, not per row.** One upstream mistake reaches several recipes —
  `transitionDuration: "normal"` is in four — and a preset bump repairs them one at a time.
- **An entry that matches nothing fails**, exactly as `check:context-budget`'s `stale-allowance`
  does. An upstream repair nobody notices is one nobody can act on.
- **A row's shape is validated at runtime.** No `tsc` pass in this repo reads a root config file, and
  a row missing `property` would match nothing, read as stale, and be deleted instead of fixed.

**Nothing is filed and nobody is contacted** for any row in it — this is an independent port
(`decisions.md` **D-110**).

**Failure output.** One block per rejected declaration: the sheet and line, the selector, and the
declaration as written. Then the repair, which is different depending on where it came from — an
atomic class name spells out what produced it (`.direction_Previous` is `direction="Previous"`), and
a recipe-body declaration owes a register row instead. The success line prints the declaration count,
the distinct-pair count, the Chromium version, the allowances used, and both skip counts, because
**an allow-list that silently grew and a scanner that silently stopped finding declarations both
look like a green check** (§3.6's footer, same reason).

---

**What the first run found**, measured on 2026-08-10 against `@chakra-ui/panda-preset@3.36.1` and
Chromium 151:

| Where | Declarations rejected | |
|---|---|---|
| **Our own source** | 2 | `direction: Previous` / `direction: Next` in the docs app |
| **`@chakra-ui/panda-preset`** | 5 distinct, over 9 recipe rules | `transition-duration: normal`, `transition-timing-function: default`, `font-feature-settings: pnum`, `background: currentBg`, `not-last: var(--line-offset)` |
| **Panda's preflight** | 2 | `-moz-osx-font-smoothing`, `-moz-tab-size` — correct for Firefox, unknown to Chromium |
| **Obsolete vendor property** | 1 | `-webkit-overflow-scrolling: touch` in the ScrollArea recipe |

The first row is the one the check exists for. `MdxPagination` passed a `direction` prop to a
capitalized component; Panda's `jsxStyleProps: "all"` extracts style props from **any** capitalized
JSX component, `direction` is a real CSS property, and `"Previous"` is not one of its two values. It
was repaired by renaming the prop, in the commit that introduced the check.

`not-last: var(--line-offset)` is the widest of the upstream five: `_notLast` is not a condition this
config's Panda knows, an unknown condition key is emitted as a kebab-cased property, and the
`margin-inline-end` it was guarding is lost. The sheet carries no `:not(:last-child)` rule anywhere,
which is how it was found.

**The oracle was verified against the parser, not assumed.** For each rejected pair, the same engine
was asked to parse `selector { property: value }` into a `CSSStyleSheet` and report the resulting
value: every one came back empty, and `color: red` came back `red`. So `CSS.supports` false and *the
declaration is dropped* are the same fact here rather than a proxy for it.

**The scanner was verified against an independent count.** Panda writes one declaration per line, so
a line-shaped count is a second measurement of the same quantity: **6,106 / 6,106** on our sheet and
**6,468 / 6,468** on the docs app's. The first version did not handle the escapes in a class name and
swallowed the rest of the file at the docs app's own
`.\--content-height_calc\(100dvh_-_var\(--header-height\)\)` — the `(` opened a paren group that
never closed. It read **5,890** declarations instead of all of them, missed the `direction` finding
entirely, and reported green. That is now a unit test.

**Blind spots, five:**

- **A custom property is accepted unconditionally.** `CSS.supports("--anything", "at all")` is true,
  so `style={{ "--w": w }}` with `w="var(--w)"` — `plan.md` §3.5's third route — is invisible here in
  both directions. The check cannot tell a live custom property from a dead one, and 3,518 of the
  sheet's declarations are skipped for this reason.
- **`var(--…)` is accepted whether or not anything defines it.** `width: var(--nope)` passes. Every
  resolved token reference in the sheet is a `var()`, which is exactly why the check finds the
  *unresolved* ones — Panda emits those as the bare token name.
- **One engine's answer.** A declaration correct for Firefox or Safari and unknown to Chromium is a
  rejection here, which is what the three vendor-prefixed rows in the register are. A property
  Chromium supports and another engine does not is invisible.
- **A value gated behind `@supports` is judged like any other.** Nothing in either sheet is today, but
  a deliberate `@supports not (…)` fallback would be reported and would need a register row —
  the check reads the declaration, never the guard around it.
- **A supported declaration can still be the wrong one.** `mt="8"` where `mt="4"` was meant parses
  perfectly. This check answers *does it parse*, never *is it what you meant*; the artefact for that
  is a computed-style assertion (§2.2).
